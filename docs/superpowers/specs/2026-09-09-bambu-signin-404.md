# Bambu account sign-in: 404 when signing in with Google

Branch: `fix/bambu-signin-404` (from `feat/ultra-preferences`)
Reference: BambuStudio `66e405477` (2026-08-31), `SLIC3R_VERSION 02.08.02.61`, read-only clone at `C:\Dev\BambuStudio`.
Our `SLIC3R_VERSION`: `01.10.01.50`.

## Symptom

Users of released 2.3.6.5 / 2.3.7.0 get a **404 when signing in to a Bambu account with
Google** - the third-party button inside the Bambu sign-in dialog. Two fixes already in the
release (bare `/sign-in` instead of the localed URL; a `BBL-Slicer/v02.03.00.01` UA on the
login webview) no longer suffice.

## How the flow actually works

1. The dialog (`ZUserLogin`) opens a webview on `<bambulab host>/sign-in`. The site chooses
   its **in-slicer** login flavour by sniffing `BBL-Slicer/v<version>` out of the webview's
   User-Agent.
2. Clicking a third-party provider makes the page send `get_localhost_url`. We answer with
   the base URL of our **loopback HTTP server**, then `start_http_server()`.
3. The page sends `thirdparty_login` with a URL, which we hand to the **system browser**
   (`wxLaunchDefaultBrowser`). The webview is out of the picture from here.
4. Google authenticates the user, bambulab redirects the browser to the slicer's loopback
   with `?ticket=<t>&redirect_url=<url>`.
5. The loopback exchanges the ticket (`agent->get_my_token`), fetches the profile, calls
   `change_user`, and **302s the browser back to `redirect_url?result=success|fail`**.

Step 4 is the one that breaks, and it breaks *in the system browser* - which is exactly
where the user sees a bare 404 page.

## Diff against current Bambu Studio

### 1. Loopback port - 13650 vs 13618 (most likely cause)

`GUI_App::start_http_server()` in our fork did `m_http_server.setPort(13650)`, with a
comment reasoning that bambulab redirects to "whatever localhost port we report" via
`get_localhost_url`. Upstream binds `LOCALHOST_PORT` = **13618** and reports exactly
`LOCALHOST_URL + LOCALHOST_PORT` - a compile-time constant, never the bound port.

That upstream constant is the tell. If the site honoured the advertised base URL, upstream
would have no reason to hard-code it; it hard-codes it because **13618 is the registered
redirect target on bambulab's side**. The third-party leg is an OAuth-style redirect
arriving from the *system browser*, and its destination is fixed server-side - an
advertised `http://localhost:13650` is not a registered redirect URI, so bambulab either
refuses it or sends the browser to `localhost:13618`, where our server is not listening.
Either way the browser lands on a 404 (or a connection error) rather than on our handler.

This also explains why the two earlier fixes did not help: they both act on the *webview*
(steps 1-3), while the failure is in step 4, in a different process entirely.

### 2. User-Agent layout

| | ours (before) | upstream |
|---|---|---|
| order | `BBL-Slicer/v.. (theme) Mozilla/5.0 ..` | `Mozilla/5.0 .. Edg/107.0.1418.52 BBL-Slicer/v.. (theme) BBL-Language/<lang>` |
| version | `02.03.00.01` (spoof) | `SLIC3R_VERSION` = `02.08.02.61` |
| language token | absent | `BBL-Language/<primary subtag>` |

Ours put the BBL token **first**, so the string does not start with `Mozilla/5.0`, and
omitted `BBL-Language` entirely. Any sniffing anchored on the Mozilla prefix, or that reads
the language token, sees a UA it does not recognise. And `02.03.00.01` is a guess at where
the gate sits; upstream's shipping version is `02.08.02.61`, so a gate that has moved above
`02.03.00.01` would silently drop us back to the retired legacy flow.

### 3. Loopback answering a login callback with 404

`HttpServer::bbl_auth_handle_request` fell through to `ResponseNotFound` whenever the token
exchange failed - a bad or expired ticket, a network blip, no agent. Upstream **never**
404s a well-formed ticket callback: `session::handle_login` 302s to
`redirect_url?result=fail` and only 404s when the params could not be parsed at all. So on
our side, any failed exchange *also* surfaced as a 404 in the browser, indistinguishable
from the port problem and masking whatever the real error was.

### 4. `/refresh_token` route

Upstream routes `/refresh_token` (Agora GoLive camera URLs) away from the login handler.
Ours had no such route, so a `/refresh_token` hit went to the login handler and 404ed.
Not a sign-in cause, but the same 404 with a different origin.

### 5. `get_localhost_url` base URL spelling

Both sides use `http://localhost:` (not `127.0.0.1`) - ours already did this by hand. Kept,
now via a named constant.

### 6. `OnScriptMessage` command parity

Commands handled: `user_login`, `user_ticket_login`, `get_localhost_url`, `thirdparty_login`,
`new_webpage` - **the same set on both sides**. Upstream delegates the first two to
`GUI_App::handle_script_message` (which for `user_ticket_login` runs `TicketLoginTask`
async); ours inlines the equivalent ticket exchange in the dialog. Functionally equivalent,
so left alone. Ours additionally keeps `autotest_token`.

Upstream also loads the **localed** `/sign-in` (`current_language_code_safe()`); our release
deliberately loads the bare one. Left as-is: the localed callback 404 that motivated that
change is a real, separately observed failure, and upstream guards the locale with
`current_language_code_safe()` (a validated list) which we do not have.

## What changed

- **`src/slic3r/GUI/GUI_App.cpp`** - bind `LOCALHOST_PORT` (13618) again instead of 13650,
  with the reasoning above. Added the test-only `SNORCA_LOGIN_LOOPBACK=1` knob that starts
  the loopback at startup so its routes can be gated without credentials.
- **`src/slic3r/Utils/LoginUserAgent.{hpp,cpp}`** (new) - wx-free
  `bbl_login_user_agent(platform, dark, language_code, brand_tag, slicer_version)` producing
  upstream's exact token layout, plus the single constant `BBL_LOGIN_UA_VERSION =
  "02.08.02.61"` documented as *must track the Bambu Studio version bambulab.com gates on*.
  The `brand_tag` parameter preserves the owner's requirement that the `BBL-Slicer` /
  `SM-Slicer` tokens stay: only `BBL-Slicer` reports the gated version, everything else
  still reports our own `SLIC3R_VERSION`.
- **`src/slic3r/GUI/Widgets/WebView.cpp`** - all three UA sites (Windows, macOS/Linux
  create, `RecreateAll`) now go through that builder.
- **`src/slic3r/GUI/HttpServer.{hpp,cpp}`** - route `/refresh_token` away from the login
  handler; a well-formed ticket callback whose exchange fails now 302s to
  `redirect_url?result=fail&error=ticket_exchange_failed` like upstream, and a ticket with
  no `redirect_url` gets a readable 200 failure page (`ResponseLoginFailed`) instead of a
  404. Unknown paths still 404. Added `BBL_LOGIN_LOCALHOST_URL`.
- **`src/slic3r/GUI/WebUserLoginDialog.cpp`** - `get_localhost_url` answers with
  `BBL_LOGIN_LOCALHOST_URL + <bound port>` and logs an **error** if the bound port is not
  13618 (another slicer holding it), so the cause is visible in the log instead of showing
  up as a browser 404.

Our own extra loopback routes are untouched: the WCP download prefix, `/localfile/` and
`flutter_web` all live in `web_server_handle_request` on the **page** server (13619), a
different server from the auth loopback.

## Proofs

- **`tests/slic3rutils/login_useragent_tests.cpp`** (Catch2, 7 cases) pins the UA
  byte-for-byte against Bambu Studio's format for Windows and macOS, asserts the browser
  prefix comes first and the BBL tokens last (the exact regression), that the gated version
  is reported regardless of the slicer version passed in, that non-`BBL-Slicer` brands keep
  our own version, and that the language token is the bare primary subtag with an `en`
  fallback.
- **`C:\Users\acesa\AppData\Local\Temp\snorca_hubtest\test_login_loopback.py`** starts one
  scratch instance (`dd_signin`, copied from `dd_ctl`, hidden, `SNORCA_LOGIN_LOOPBACK=1`),
  then drives the loopback with **fake tickets only - no credentials, no real sign-in**:
  the server listens on 13618 and not 13650; a well-formed ticket callback returns 302 to
  `redirect_url?result=fail` and **not 404**; a ticket without `redirect_url` returns a 200
  failure page and not 404; `/refresh_token` is routed; an unknown path still 404s. It stops
  only its own instance, by PID.

## Owner test script (live install, requires signing in)

1. Make sure **no other slicer is running** - Bambu Studio and OrcaSlicer also bind 13618,
   and whichever started first wins the callback. Check with
   `netstat -ano | findstr :13618` (should be empty before EdgeSlicer starts).
2. Start EdgeSlicer, open **Account -> Log in**, and click **Sign in with Google**. The
   system browser opens.
3. Complete the Google sign-in.

**Expected:** the browser lands briefly on a `localhost:13618` URL and is immediately
redirected back to a bambulab page with `?result=success`; the slicer's sign-in dialog
closes and the Account menu shows the account.

**If it still 404s, capture:**
- **The URL bar of the 404 page.** This is the decisive evidence:
  - host is `localhost`/`127.0.0.1` with a port that is **not 13618** -> the advertised port
    is being honoured after all and the site sent the browser somewhere we do not listen;
  - host is `localhost:13618` -> our loopback is not listening (check step 1) or answered
    404; grep the log for `thirdparty_login`;
  - host is `bambulab.com/...` -> the site itself 404ed; note whether the path contains a
    locale prefix (`/en-us/...`) and whether it is `sign-in/callback` (legacy, means the UA
    gate rejected us) or `sign-in/studio-callback` (current flow).
- **The slicer log lines around `thirdparty_login`** - `get_localhost_url`, the
  `loopback bound to port ... instead of 13618` error if present, `get_my_token failed`,
  and the redirect that was issued.
- If the URL bar shows a `bambulab.com` 404 with the legacy `sign-in/callback` path, the
  version gate has moved again: bump `BBL_LOGIN_UA_VERSION` in
  `src/slic3r/Utils/LoginUserAgent.hpp` to the current Bambu Studio `SLIC3R_VERSION` and
  retest - that constant exists for exactly this.

## Honest limits

The port claim is inferred from upstream's code (a hard-coded constant where a dynamic
value was available, and the `NEW:httpserver listen on 127.0.0.1` and
`ENH: use ticket instead of token` upstream commits), not confirmed against bambulab's live
behaviour - confirming that would require actually signing in, which was out of scope here.
The UA and 404-response fixes are certain divergences from upstream regardless of which one
is the trigger; the port is the one that best explains a 404 appearing in the *system
browser* rather than in the webview.
