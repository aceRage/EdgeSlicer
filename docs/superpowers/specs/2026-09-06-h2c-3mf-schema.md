# The sliced-3MF metadata schema an H2C requires

Date: 2026-09-06
Branch: `feat/h2c-3mf-schema` (from `origin/feat/ultra-preferences`)
Upstream reference: `C:\Dev\BambuStudio` at `66e405477` (2026-08-31), which has full H2C support.
All upstream line numbers below are from that commit.

## The evidence

A real H2C (serial prefix `31B`, `model_id` `O1C2`) took a plate 3MF from this fork over LAN and
stopped with **HMS 05004046**. The text for device 31B
(`C:\Dev\BambuStudio\resources\hms\hms_en_31B.json`) is:

> The print has stopped because the 3MF file is invalid. Please verify that the correct printer
> model was selected during slicing, or update Studio and re-slice the file.

The rejected file's `Metadata/slice_info.config` (plate 8, project "0930 - Bellibolt", printer
preset "Bambu Lab H2C 0.4 nozzle") was:

```xml
<plate>
  <metadata key="index" value="8"/>
  <metadata key="printer_model_id" value="O1C2"/>
  <metadata key="nozzle_diameters" value="0.4,0.4"/>
  <metadata key="nozzle_volume_type" value="0"/>
  <metadata key="timelapse_type" value="0"/>
  <metadata key="prediction" value="3079"/>
  <metadata key="weight" value="12.69"/>
  <metadata key="outside" value="false"/>
  <metadata key="support_used" value="true"/>
  <metadata key="label_object_enabled" value="true"/>
  <metadata key="filament_maps" value="1 2 2 2 2 2"/>
  <object identify_id="1800" name="Black.stl" skipped="false" />
  <filament id="1" tray_info_idx="P3beb2e8" type="PLA" color="#000000" used_m="4.19" used_g="12.69" />
  <warning .../>
</plate>
```

`printer_model_id` is correct, so the HMS text's "wrong printer model" wording is a red herring:
the second half — "update Studio and re-slice" — is the real cause. This is the pre-2.x
(single-nozzle) schema.

## Why the H2C is stricter than the H2D

The H2D and the H2C both have two extruders, but the H2C's second extruder is a **multi-nozzle**
extruder. From this fork's own profile
`resources/profiles/BBL/machine/Bambu Lab H2C 0.4 nozzle.json`:

```json
"extruder_max_nozzle_count": ["1", "6"]
```

The H2D profile sets no `extruder_max_nozzle_count` (i.e. one nozzle per extruder). So on an H2D,
`filament_maps` ("which extruder does each filament use") fully determines the physical hotend. On
an H2C it does not: a filament assigned to extruder 2 could be in any of six nozzles. The upstream
schema carries that missing information in two places the fork never wrote:

* `<filament ... group_id="N" nozzle_diameter="0.4" volume_type="Standard" .../>` — the logical
  nozzle(s) each filament may run on.
* `<nozzle id="N" extruder_id="2" nozzle_diameter="0.4" volume_type="Standard"/>` — the logical
  nozzle table itself.

That is the single most plausible reason the same writer output is accepted by an H2D and rejected
by an H2C, and it is the core of this port.

### `Metadata/filament_sequence.json`
Upstream writer: `_BBS_3MF_Exporter::_add_filament_sequence_file_to_archive`, 9070-9110
(the `nozzle_sequence` key is written at 9091). **The fork wrote no such file at all.** The task
brief called this "plate_N.json nozzle_sequence"; the actual location is
`Metadata/filament_sequence.json`, keyed `plate_1`, `plate_2`, ... - `Metadata/plate_N.json` is the
bbox/thumbnail sidecar (`PlateBBoxData::to_json`, `src/libslic3r/GCode/ThumbnailData.hpp:87`) and
carries no nozzle data upstream either. Contents:

```json
{"plate_1": {"sequence": [1,2], "nozzle_sequence": [0,1], "optimal_assignment": []}}
```

The key is `"sequence"` normally and `"filament_sequence"` only when the plate was grouped with a
dynamic (selector-driven) nozzle map.

### `Metadata/plate_N.json`
Only one field differs: upstream `PlateBBoxData` carries `first_layer_time`
(`src/libslic3r/GCode/ThumbnailData.hpp:83,97`); the fork's struct has no such member. No
nozzle-related field exists here upstream. **Not ported** (see "Not ported" below).

### G-code
* `;VT<filament_id> H<nozzle_id>` right after the machine start G-code — upstream
  `src/libslic3r/GCode.cpp:3016`, parsed back at `GCode/GCodeProcessor.cpp:1033`. Marks the first
  filament of the print and the logical nozzle it runs on. `H` is `-1` when the plate has no
  dynamic nozzle map (upstream macro `NOZZLE_ID_FOR_GCODE`, `GCode.cpp:117`). **The fork wrote
  nothing.**
* `T<n> H<m>` on tool change already comes out right: it is emitted by the H2C's own
  `change_filament_gcode` template (`T[next_filament_id] H[next_hotend]`), and the fork already
  binds `next_hotend`.
* The `; CONFIG_BLOCK` is generated from the full config, so every H2C key present in the preset is
  already written; no upstream-specific header lines are missing there.

### Project-side (`Metadata/model_settings.config`)
Upstream also writes per-plate `filament_volume_map` and `filament_nozzle_map` metadata alongside
`filament_maps` (8398-8420). The fork writes only `filament_maps`. This affects project reload
fidelity, not the printer, and is **not ported** here.

### Other H2C-specific upstream code paths, for the record
Not part of the 3MF schema, but this is what upstream does differently for an H2C and the fork does
not; each is a separate piece of work:
* `ToolOrdering.cpp:1884` `fmmNozzleManual` (manual per-nozzle assignment) and 1955-2030 /
  2797 the dynamic (selector) per-layer nozzle planner. The fork always produces a **static**
  grouping, which is a configuration upstream also supports.
* `Print.cpp:3820` prime-volume saving mode; `PartPlate.cpp` / `ConfigManipulation.cpp` H2C UI
  branches.

## What was ported, and how it maps onto the fork's data model

The fork already has upstream's `MultiNozzleUtils` verbatim (`src/libslic3r/MultiNozzleUtils.hpp`
is byte-identical to upstream's) and its own port of the grouping engine in `ToolOrdering.cpp`, so
the values exist - they were just never carried into the 3MF. Four adaptations were needed:

1. **The grouping result lives on `Print`, not on `GCodeProcessorResult`.**
   Upstream: `GCodeProcessorResult::nozzle_group_result` -> `PlateData::parse_filament_info`.
   Fork: `ToolOrdering::reorder_extruders_for_minimum_flush_volume` stores it with
   `Print::set_nozzle_group_result`, read back with `Print::get_layered_nozzle_group_result()`.
   So `PlateData::nozzle_group_result` and the per-`<filament>` `group_id` / `nozzle_diameter` /
   `volume_type` are filled in `PartPlateList::store_to_3mf_structure` (right after
   `parse_filament_info`, where the `Print*` is already in hand) using upstream's exact
   diameter/volume-type reduction logic, instead of inside `parse_filament_info`.

2. **`used_for_object` / `used_for_support`.** Upstream tracks these per filament in
   `GCode.cpp:5175,5422` into `GCodeProcessorResult::used_filaments`, machinery the fork does not
   have. The fork does track `PrintEstimatedStatistics::model_volumes_per_extruder` and
   `support_volumes_per_extruder`, which carry the same fact; the attributes are derived from those
   (non-zero volume == used).

3. **`filament_maps` padding.** Upstream always has a full-length `filament_map`. The fork leaves
   it short on classic single-nozzle machines, and its previous writer padded with `1`. The padding
   is kept so single-extruder output is unchanged; when the grouping engine ran (H2D/H2C/X2D) the
   vector is already full length and the padding is a no-op.

4. **`;VT` gating.** Upstream always has a nozzle group result and so always writes `;VT`. The fork
   only has one for grouping-model machines, so the line is written exactly when
   `Print::get_layered_nozzle_group_result()` is non-null - H2C, H2D and X2D get it (matching real
   Bambu Studio output for those machines), and P1S/A1/X1C G-code is byte-identical to before.

Everything else is a faithful port: same attribute names, same order, same conditionals
(`limit_filament_maps` and `default_ams_type` are emitted by the same `if`s upstream uses; they
stay absent here because no BBL preset in this fork's profile set defines `default_ams_type` and
nothing populates `limit_filament_maps` - upstream run against the same profile data would omit
them too).

New/changed source:
* `src/libslic3r/Format/bbs_3mf.hpp` - `PlateData` gains `nozzle_volume_types`,
  `first_layer_time`, `support_material_on_wipe_tower`, `filament_maps`, `limit_filament_maps`,
  `filament_change_sequence`, `nozzle_change_sequence`, `optimal_assignment`,
  `nozzle_group_result`, `nozzles_info`.
* `src/libslic3r/Format/bbs_3mf.cpp` - the ported writer, `add_vector` / `parse_int_list` /

  `first_layer_time` / `support_material_on_wipe_tower` / `limit_filament_maps` plate metadata).
* `src/libslic3r/ProjectTask.hpp` - `FilamentInfo` gains `used_for_object`, `used_for_support`,
  `total_load_time`, `total_unload_time`.
* `src/libslic3r/Print.hpp/.cpp` - `Print::support_material_on_wipe_tower()`, ported verbatim from

## Not ported (and why)

| Upstream item | Reason |
| --- | --- |
| `<pause_list>`, `pause_count` value | No pause-print model in this fork (`GCodeProcessorResult::pause_printing`). `pause_count` is written as a constant `0`, which is what upstream writes for a plate with no pauses. A plate with a real pause would under-report. |
| `<ams_list>`, `default_ams_type` | Depend on the `ams_filament_load_time_*` / `default_ams_type` printer-config keys, which exist in neither this fork's `PrintConfig` nor upstream's own BBL profile JSONs. Upstream's conditionals would omit them on this data too. |
| `<filament total_load_time/unload_time>` values | Same source (`PrintEstimatedStatistics::load_time_per_filament`) - upstream fills them from the AMS-time model in `GCodeProcessor::handle_filament_change`, which needs the `NozzleStatusRecorder` machinery the fork lacks. The attributes are written with value `0`. |
| `<mixed_filament>` | The fork has no mixed (virtual) filaments (`filament_mixed_components` is not a config key here). Upstream omits the tag when the list is empty. |
| `<layer_filament_lists>` | Needs `GCodeProcessorResult::layer_filaments`; the fork does not persist per-layer filament sets out of `ToolOrdering`. Upstream omits the block when empty. |
| `optimal_assignment` in `filament_sequence.json` | Upstream computes it from a filament-change time model (`GCode.cpp:3482-3500`) built on the same AMS-time machinery. Written as an empty array. |
| `plate_N.json` `first_layer_time` | `PlateBBoxData` has no such field in this fork; the value is carried in `slice_info.config` instead, which is where the printer reads it. |
| Dynamic (selector) nozzle mapping | The fork's grouping always produces a static map, so `enable_filament_dynamic_map` is `false` and `nozzle_sequence` is the static per-filament nozzle. This is a supported upstream configuration, not a schema violation - but if the H2C requires a dynamic map to use more than one nozzle on extruder 2, that is the next piece of work. |

## Two more adaptations found while building this

### `extruder_type` / `nozzle_volume_type` are not sized to the extruder count here
BambuStudio resizes every key in its `printer_extruder_options` set (`PrintConfig.cpp:7513`,
"Parameters that are the same as the number of extruders") to the extruder count when a printer
preset loads, so upstream always has one value per extruder. This fork has no such resize, and
`extruder_type` is additionally in `PrintConfigDef::handle_legacy`'s obsolete-key ignore set
(`PrintConfig.cpp:8057`), so the `"extruder_type": ["Direct Drive", "Direct Drive"]` that
`fdm_bbl_3dp_002_common.json` really does declare is *dropped on load* and the config keeps the
one-element default. Writing that straight out would have produced `extruder_type="0"` for a
two-extruder machine - the same malformed shape as the scalar `nozzle_volume_type` the H2C
rejected. The writer therefore pads both vectors to `nozzle_diameter.size()` before serialising
them. Un-retiring `extruder_type` in `handle_legacy` would be the deeper fix and is left alone
here.

### A machine with no grouping result still needs per-filament nozzle attributes
Upstream always has a `LayeredNozzleGroupResult`, even on a single-nozzle printer, so its
`<filament>` tags always carry `group_id`, `nozzle_diameter` and `volume_type`. This fork only
computes a grouping for machines where `support_different_extruders()` is true (H2D/H2C/X2D). Left
alone, a P1S would have got `group_id=""` and `nozzle_diameter="0.00"` - present but empty, which
is worse than absent. `PartPlateList::store_to_3mf_structure` therefore fills the single-nozzle
case explicitly (`group_id={0}`, the printer's first nozzle diameter and volume type), which is
exactly what upstream's single-nozzle grouping result would have produced. The `<nozzle>` table is
*not* synthesised for those machines: it has no source here.

### The importer's plate-copy list dropped the fields
`_BBS_3MF_Importer` parses `slice_info.config` onto `m_plater_data`, then hand-copies a fixed list
of fields into the returned `PlateDataPtrs` (bbs_3mf.cpp, both the project loader and
`load_gcode_3mf_from_stream`). Anything not on that list is silently lost - which is why the first
version of the round-trip test saw the `<filament>` attributes come back but not the plate
metadata. The list now also copies `nozzle_volume_types`, `nozzles_info`, `filament_maps`,
`limit_filament_maps`, `filament_change_sequence`, `nozzle_change_sequence`,
`optimal_assignment`, `support_material_on_wipe_tower` and `first_layer_time` (upstream copies the
same set), plus `printer_model_id` / `nozzle_diameters` in the project loader, which the gcode-3MF
loader already copied.

## Blockers found in the fork while proving this (all pre-existing, none introduced here)

1. **Every BBL 2.x process preset fails CLI validation.** `prime_tower_brim_width` is `-1` ("Auto")
   in every `@BBL H2C` / `@BBL H2D` process JSON, but this fork's `PrintConfigDef` sets
   `def->min = 0` (`PrintConfig.cpp:6757`); upstream sets `min = -1` with an "Auto" enum label
   (`BambuStudio PrintConfig.cpp:6248`). `m_print_config.validate(true)` therefore rejects the
   preset and the CLI exits `CLI_INVALID_VALUES_IN_3MF`.
2. **`Print::is_BBL_printer()` is set after `print->validate()` in the CLI.**
   `Snapmaker_Orca.cpp:5292` validates, `:5382` sets the flag - so a BBL printer is validated as a
   non-BBL one and hits Orca's "relative extruder addressing requires G92 E0 in layer_gcode" check,
   which BBL profiles legitimately do not satisfy.
3. **Slicing a grouping machine with two filaments actually in use crashes.** H2D and H2C both
   die with an access violation (0xC0000005) as soon as a second filament is used - reproduced
   with `--sparse-infill-filament=2` and with a separate support filament, on the H2D and the H2C,
   on **both** this build and the pre-change baseline build; the P1S with the same two filaments
   is fine. The stack could not be symbolised (minidbg did not load the DLL's PDB). Because of
   this, the H2C proof above uses a single filament in use: **a plate with two filaments on two
   different nozzles could not be sliced at all**, so the multi-nozzle values in `<filament
   group_id>` / `<nozzle>` are demonstrated by the Catch2 round-trip case rather than by a real
   two-nozzle slice.

## HMS resource files (optional item): not applicable

This fork's HMS loader has no device-suffixed file naming and no `resources/hms` fallback:
`HMSQuery::get_hms_file(hms_type, lang)` (`src/slic3r/GUI/HMS.hpp:29`) takes no device id, and both
`load_from_local` and `save_to_local` read and write only `<datadir>/hms/`
(`src/slic3r/GUI/HMS.cpp:110,143`). Upstream's signature is
`get_hms_file(hms_type, lang, dev_id_type)` and it ships `resources/hms/hms_<lang>_<dev>.json` plus
`hms_action_<dev>.json`. Copying `hms_*_31B.json` into `resources/hms` here would therefore do
nothing - the files would never be read. Nothing was copied.

## What is not verified

The only real acceptance test is the user's H2C. Everything here is verified against the upstream
*writer source*, because upstream cannot be run in this environment: the checklist in the proof
section is derived tag-by-tag from `bbs_3mf.cpp:8630-8890`, not from a Bambu-Studio-produced file.
Which of these fields the firmware actually validates is inference from the machine's capabilities
(the "Printer-validatable?" column above), not from firmware behaviour.
